# Core Collection Identity Remap 2026

Same gap as `benchmark-identity-remap-2026` (see that directory for full
method writeup), found while preparing Evidence ETL v1: `corpus/core-
collection.json`'s 31 records also lacked a `posi_id` field — Evidence
records need to key against canonical `POSI-J-######` identities, and this
was a blocking prerequisite, not optional cleanup.

## Merge Gate

```

Matched by ISSN-L:        29

Matched by OpenAlex:      0
New POSI-J minted:        0
Manual review:            0 / 31

Identity-layer validation:
31 / 31 valid

POSI-J format invalid:       0
Duplicate POSI-J assignment: 0
```

Same method as the benchmark remap: internal dedupe first
(`buildCandidateEntities()`), then value-based registry join (not
strict-tier), zero minting — any unresolved entity would go to manual
review, not a guess. All 31 resolved cleanly against the existing
registry (expected, for the same reason as the benchmark set: the recent
23,331+874-record migration explicitly minted for both
`core-collection.json` and `global-benchmark.json`).

`corpus/core-collection.json` gains a `posi_id` field per record
(additive — existing `id`/`journal_code` untouched), generated by the
same `posi-engine` script:
`scripts/remap-benchmark-identity-2026.mjs --registry
registry/journal-id-map.csv --benchmark corpus/core-collection.json`.
